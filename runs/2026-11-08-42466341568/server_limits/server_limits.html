How hard can you push each server before it gives up?

One fixed open62541 C client, escalating load (client processes x async pipeline depth) against each server implementation's default configuration until it errors, its tail latency blows up, its throughput collapses, or it dies. See server_limits/README.md for exactly what each of those means.

The short version

Every server was given more and more work until it could not keep up. Each bar is the most work that server got through while still answering everything on time.

1. How does completed work scale with load?

Each point is one measured load level. A hollow marker is a level that beat the server.

2. Where does each implementation's edge sit?

Every load level tried, laid out by client-process count and per-client pipeline depth.

3. Which implementation went furthest?

Concurrent requests in flight (clients x outstanding) at the heaviest load level that still held. The table adds the capacity reading: peak throughput, and the cheapest load that already reaches it.

What each verdict means

The five criteria a load level is judged against, and the thresholds this particular run used. A level trips as many of them as apply.
CodeVerdictWhat it measuresTripped in this run when…
errerror/timeout rateThe share of this level's calls that timed out, came back an error, or were never answered at all. A client that could not even connect counts as one failed call rather than dropping out of the totals, so a server that has stopped accepting sessions shows up here rather than as missing data — which also means a level nothing could reach at all lands here at 100%. The 'how it failed' column separates the two.more than 1% of calls failed
p99p99 latency blow-upThis level's 99th-percentile latency measured against the p99 at the lightest load this implementation was run at (1 client, 1 outstanding). It catches the server that is still answering every single call, and correctly, but has stopped answering promptly — which no error count would ever show. Read it together with the throughput: a level that tripped this while its calls/second sat at the implementation's peak, with no errors, is a server at capacity and queueing normally — latency rising in proportion to the requests in flight is arithmetic, not a fault — rather than one in trouble. The lightest-load p99 it is compared against is named under each frontier above, and is measured rather than configured, so a noisy server wants 'samples' raised before it is trusted.p99 grew past 10x that implementation's own lightest-load p99
thrthroughput collapseSuccessful calls per second against the previous pipeline depth at the same client count. It catches the point where offering the server more work makes it complete less — the queue is now costing more than it buys. Compared within one client count only, since a new row restarts at depth 1 and is genuinely less concurrent than the row before it.completed work fell below 50% of the previous depth
netconnection brokenA connection that was already established died in the middle of the level — the secure channel closed, or the socket dropped — rather than any individual call coming back bad. It does not mean the server never ran: a server that failed to start never produces a load level at all (it is listed in the banner at the top of this page), and one that refused the connection outright is counted as a failed call, so it reads as err. A call the load generator itself declined to send is not a verdict at all — it is recorded as a harness failure in the banner above. Read a net at the very top of a ramp with some suspicion even so: the machine running out of sockets or file descriptors looks the same from the client side as the server hanging up.any client lost a connection it had already made
deadserver process diedThe server process did not survive the level. Unlike the four above, which infer distress from what the client saw, this is the server observably gone, so it ends that implementation's ramp on the spot instead of only ending the row. Not always a capacity limit: an o6\Python server on an evaluation licence exits by itself after ten minutes, which looks identical from here, so check the run's wall-clock before reading it as one.the server process exited

Each load level was measured for 5 s after a 3 s untimed warm-up, with a per-call timeout of 2000 ms and 2 s of grace for calls still in flight when the window closed — anything still unanswered by then is counted as failed, not waited for. Each level was measured 7x, and the median of those decides the verdict.

Where a level tripped more than one criterion, the heatmap cell above shows the most severe and marks it with a +; severity runs in the order listed here read upwards — the server being gone outright outranks a dropped connection, which outranks failing calls, which outranks work going down, which outranks merely having become slow. The full list is always in the hover and in the tables.
